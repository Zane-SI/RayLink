## 公网实验与撤回

用户提供的 Cloudflare Token 可以管理 DNS，因此临时增加了一个代理备用域名，
并验证源站证书。该域名未写入正式订阅。账户隧道、Workers 与相关设置 API
返回 403；用户当前无法网页登录，没有取得这些操作权限。

隔离 Mihomo 客户端绑定 Mac 的物理 `en0`，关闭其 TUN，不修改用户当前活动订阅，
保持 Cloudflare 动态解析和证书校验。新域名上的普通 WS、early-data、Chrome
指纹以及 IPv4 / 默认地址选择均未通过重复请求测试。单次 20 请求的 early-data
候选收到 6 次 HTTP 响应，Chrome 变体收到 13 次，其余为超时或断连；HTTP 响应
包含 API 的 401 与验证页，不能作为应用成功率。

同时间六请求对照也均有失败：普通 WS 默认地址选择 5 次响应、仅 IPv4 3 次，
early-data 默认地址选择 5 次、仅 IPv4 4 次。这些小样本仅用于否定“改一个参数即可
消除超时”，不能推算长期可用率或证明 GFW / 运营商拦截。HTTP/2 候选也未形成
通过源站到公网的验收链路，未采用。临时 Quick Tunnel 的既有成功记录不代表
一个可发布、可持久使用的固定入口。

所有未合格候选已撤回：临时域名的 DNS 记录在核对所有权后删除；Caddy、CDN
适配器及生成器恢复原始字节并核对哈希。原有七个协议的主配置及 PID 1380
始终未改，Caddy PID 667 未变；控制面仅为上述导出修正重启。

恢复后的 WS 适配器与源站均完成了真实用户认证转发请求，Google/gstatic 返回
302/204，OpenAI API 返回 401。公网复测仍出现超时，不能将源站通过等同公网稳定。

## 部署后完整订阅验收

从生产接口获得并重新下载 Mihomo、Mihomo Modern 与 sing-box 订阅。两种 Mihomo
完整配置均保留 8 个节点、原 CDN 域名、TLS/SNI/Host 关系和动态 CDN DNS，未启用
试验 early-data。使用实际下发配置的新隔离客户端测试；未固定节点、未修改活动客户端。

| 请求 | Mihomo | Mihomo Modern | 结论边界 |
| --- | --- | --- | --- |
| Google 204 | 3/3 返回 204 | 3/3 返回 204 | 网络探测可达 |
| Google 首页 | 3/3 返回 200 | 3/3 返回 200 | 可跟随 Google 的 HTTPS 跳转，无 google.cn/m 跳转 |

| OpenAI models API，无密钥 | 3/3 返回 401 | 3/3 返回 401 | 仅证明 TLS 与鉴权端点响应 |

24 次请求未观察到超时。两份配置自动选择的实际链路均为：
`普通代理 → 故障回退 → raylink-local-vmess`；
`AI 代理 → AI 稳定出口 → raylink-local-vmess`。
这证明本轮默认路径测试通过，不能证明 CDN 本身已恢复或所有网络长期稳定。
普通 Google 保留服务器出口，AI 住宅出口设置未改。

追加隔离长连接测试，沿用实际默认 VMess 节点与完整订阅的 DNS / 端点配置，
仅将测试回环目标显式送入该节点，避免被客户端局域网直连规则绕过。受控 HTTP
fixture 的 WebSocket 与 SSE 均在空闲 70 秒后收到后续数据（分别保持 70.042 秒、
70.002 秒）。这是默认节点的传输测试，不是 ChatGPT 对话或住宅上游的长连接验收。

## 使用与后续验收

更新完整订阅后，普通代理使用默认的“故障回退”，AI 代理使用默认的“AI 稳定出口”；
不建议手工锁定尚未合格的 CDN 节点。Mac 当前使用的另一份订阅未被切换。

仍需在实际客户端验证 ChatGPT 登录、发送消息和持续生成，以及 iPhone、移动网络和
Tailscale 共存。需要具备 Cloudflare 隧道权限的账户访问，才能继续验证固定隧道方案；
现有试验不足以承诺该方案会解决问题，也没有把临时隧道当作正式节点发布。
