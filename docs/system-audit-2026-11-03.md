本轮完成源码、生产服务、数据库、备份、权限、依赖、Mac 活动配置及隔离网络测试。**没有修改生产配置，没有切换 Mac 的活动订阅或策略组，没有推送或部署。**

### 安全维护的实际边界

`npm audit --omit=dev` 报告 3 个受影响包，按包汇总为 2 项高危、1 项中危；生产安装版本与锁文件一致。

- MCP 输入验证资源消耗问题：上游要求升级到至少 2.3.0，且显式启用 `maxToolInputElements`；单纯升级不生效。当前已经在 SDK 前鉴权，并限制请求体为 256 KiB、单令牌 8 并发、全局 32 并发，但部分数组及任意 JSON 选项缺少元素或深度上限，应补齐。依据：[MCP 官方公告](https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-46jr-4wx8-v453)。
- MCP 共享实例串响应公告：当前 `server/mcp.js` 已使用每次创建新 `McpServer` 的工厂模式，属于上游说明的不受该模式问题影响的实现，不能把审计条目直接解释为已发生串数据。依据：[MCP 官方公告](https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-jm63-cq47-j5jp)。
- Zod 应更新到修复集合尺寸检查顺序的版本；本次审计给出的修复范围为至少 4.6.6，同时给业务集合设置合理上限。依据：[Zod 官方修复](https://github.com/colinhacks/zod/pull/6652)。
- Hono 的静态路径二次解码条目需要随依赖更新消除；尚未确认其 `serveStatic` 功能在 RayLink 当前请求路径可达，不将其表述为已确认的公开越权漏洞。

外部未携带凭据访问管理员 API 与 MCP 初始化均返回 401，TLS 验证通过。数据库中的 27 个 MCP 令牌均已撤销；本轮没有创建令牌，因此只验证了未认证访问被拒绝，未验证当前存在可用的 Agent 管理凭据。建议界面显示“服务已运行 / 有效令牌数量 / 最近成功调用”，避免把服务在线等同于 Agent 已可用。

代码定位：`server/mcp.js` 的工厂、鉴权与并发限制；`server/mcp-tools.js:54` 的节点范围数组及 `:95` 的 JSON 高级选项；`server/database.js:338` 附近的数据库初始化。

## 网络、AI 与智能分流

### 当前生效路径

- 普通代理：`普通代理 → 故障回退 → raylink-local-vmess`。
- AI 代理：手动选中 `raylink-local-vmess`。客户端入口协议选择与服务器端住宅出口设置是两层独立决定；选择入口不会自动改变住宅配置。
- 未分类流量：进入可手动切换的兜底组，当前跟随普通代理。
- 国内规则已加载：8,858 条域名、15,365 条 IP；广告域名规则 58,417 条。
- App Store 主要内容域名已有前置直连与国内 DNS 策略；Tailscale 私网和域名已有专门处理。当前没有证据支持直接把整个 Apple/iCloud、Google 或所有未知流量都改成直连。

国内 DNS 使用 AliDNS 的两个 DoH 地址，属于同供应商冗余。未知域名采用国内答案与 IP 分类，再根据失败和地址条件启用远端解析；显式 DNS 策略优先。Mihomo 1.19.32 可并行发出备用 DNS 查询，即使最终内容请求直连。因此，“出现一次远端 DNS 查询”不能直接认定国内图片走了代理。该行为由本轮原生测试和[上游解析器源码](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/dns/resolver.go)共同支持。

当前 Mac 的 TUN MTU 为 4064，是客户端活动环境的一部分。若复现大图或应用启动问题，应测连接阶段、报文大小、PMTU、HTTP/2 与 HTTP/3 回退；没有证据前不把全局 MTU 改动当作修复。住宅链路下 AI UDP 的拒绝与应用 TCP 回退也应列入实测，但本轮尚不能将其认定为 ChatGPT App 慢的原因。

规则维护建议保持现有简洁组结构：局域网及明确国内直连，AI 独立选择，明确国外代理，未知流量兜底。使用带来源、版本和冲突检测的规则库及 DNS/IP 协同处理，按真实失败域名修正；不靠不断增加 App 名称列表覆盖未知服务。广告规则增加“最近拦截及来源”诊断，误伤需要真实拦截记录后再做精确例外。

### 公网入口对照

使用现有完整配置的隔离副本，保持原有 DNS、规则及节点参数，逐个强制选择现有 8 个入口，三个目标各两轮，共 48 次。没有修改活动客户端。

| 请求 | 原 7 个非 CDN 入口（共 14 次） | CDN 入口（共 2 次） |
| --- | --- | --- |
| Google 204 网络探测 | 全部 204；中位约 0.746 秒，范围 0.357～1.339 秒 | 全部 204；约 2.038～2.145 秒 |
| OpenAI models，无密钥 | 全部 401；中位约 1.393 秒 | 全部 401；约 3.268～3.546 秒 |
| ChatGPT 匿名首页 | 全部 403 challenge；中位约 1.507 秒 | 全部 403 challenge；约 2.804～2.921 秒 |

48 次都有 HTTP 响应，零传输超时。本网络小样本中，CDN 建连路径明显更慢，适合作备用；单次协议两轮不构成长期稳定性结论。Google 204 不等于搜索页面验收，API 401 不等于模型调用可用，challenge 也不证明账号被封或原生 App 故障。

此前失败的 Wi-Fi 当前无法返回，CDN 在该网络的根因与修复验收仍未完成。所有协议最终复用单台 VPS 的事实也意味着，多协议解决不了主机或公网 IP 本身不可达的问题。

### App Store 与 ChatGPT 的待闭环项

同日此前诊断已完成 54 次 SOCKS/TUN/完整图片请求对照，无传输错误；App Store bag 可达，两张实际 HEIC 图片完整下载并被系统解码。但原生内容页、账号和完整资源依赖尚未验收；ChatGPT 的命令行首页遇到 challenge，不能替代原生 App 登录与流式对话测试。

同日服务器住宅上游对照显示，相比服务器默认出口，部分公开请求多约 0.6～0.9 秒。这是可测的链路成本，尚不能证明它解释了用户报告的全部慢请求，也不足以据此切换用户 AI 公网出口。

应分别记录 DNS、TCP、TLS、HTTP 首包、图片完整下载、应用启动、长连接重连，并区分规则误命中、广告拦截、证书失败、网络超时、网站验证、认证和限流。保留 App Store 与 Tailscale 的直连边界、AI 独立出口及普通 Google 不走住宅的约定。

## 建议实施顺序与实用功能

1. **先补发布门槛并做安全维护**：修正 Google 断言，加入 CDN 门槛及新旧 Mihomo 矩阵，升级依赖并启用输入限制；模拟未授权、撤销、并发与有界大输入，验证正常 MCP 创建/配置操作及幂等重试。
2. **完成用户故障闭环**：以 Mac、iPhone 同一次 App Store / ChatGPT 失败为证据，找到依赖和阶段再改规则或连接行为；按同一网络、同一入口、同一出口验收，避免同时调整多层导致失去因果证据。
3. **处理运维余量**：日志限额、轮转、磁盘 80%/90% 分级告警；数据库及新 WAL/SHM 最小权限；在隔离环境恢复最新备份并验证登录、用户数、额度周期与配置预览，核验独立备份副本。
4. **优化路由与体验**：增加 DNS 供应商独立性和规则候选更新；AI 页面展示当前入口、实际选择及住宅出口状态；保留少量可见策略组和固定 AI 出口原则。

值得新增的功能均可沿用现有界面和 MCP：

| 功能 | 实际用途与约束 |
| --- | --- |
| 脱敏诊断包 | 汇总客户端/内核、配置摘要、命中规则、实际链路、阶段耗时及时间窗口；记录网络变更指纹，默认不收集 Token、URL 查询参数、UUID、密码或账号 Cookie |
| 应用故障时间线 | 只读导入客户端连接记录，把 App Store、Tailscale、AI 的失败依赖关联到同一次请求；未知保持未知，不自动扩大全域直连 |
| 分层健康状态 | 分别显示传输、业务 HTTP、住宅上游、原生应用验收；401、403 验证页和 429 分开呈现，不据验证页自动更换 AI IP |
| 配置与版本诊断 | 显示当前源提交、已部署提交、客户端配置摘要及有效令牌状态；明确手动固定节点是否绕开回退 |
| 容量与备份面板 | 日志占用、增长、规则版本、证书到期、备份校验和最近恢复演练时间可见；清理保留回滚证据 |

当前 `server/readiness.js` 的路由通过主要表示智能模式已配置、规则库通过校验；`server/app.js` 的 AI 诊断测的是控制面出口或指定上游。两者都已有价值，但不覆盖用户客户端到入口、TUN 和原生应用全链路，新功能应补足这一层。
