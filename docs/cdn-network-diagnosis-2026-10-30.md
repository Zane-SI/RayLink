# CDN 入口网络诊断 — 2026-10-30

**本轮只保存诊断结果，没有部署生产改动。原故障网络的修复尚未验收。**

## 已定位的故障阶段

早期样本中，Cloudflare TCP 建连后仍可在 TLS 握手或 WS 升级阶段超时，
尚未进入 Google / ChatGPT 的业务请求。8 次 Cloudflare 探测中 3 次超时；
同时的源站 TLS、WS 升级对照可完成，直接 VLESS 的 4 次 TLS 握手也全部完成。
源站 HTTP `/cdn-cgi/trace` 返回 404 是正常行为，不作为源站故障。

Cloudflare 自身处理的 `/cdn-cgi/trace` 也出现超时，这类失败不经过 VPS
应用转发。因此现有证据将已观察故障限定在**客户端到 Cloudflare 边缘入口段**，
不支持将其归因于 RayLink 用户 UUID、主 sing-box 配置或 Google / AI 分流规则。

失败样本同时出现 TCP 重传、乱序和拥塞窗口收缩。32 次串行／并发对照中，
两个串行批次各有 1 次失败，两个并发批次各 8 次通过；不能断定并发数是根因。
TLS 会话复用对照中冷、热连接各 6 次均完成，没有形成可靠的修复依据。
MSS 参数实验未形成可用结论，没有据此调整系统 MTU 或客户端默认值。

**尚未确认的责任环节：**现有证据不足以区分运营商路径、其他中间网络设备、
GFW 或 Cloudflare 边缘侧问题。不能把“重传”直接当成 GFW 拦截的证明。

## 网络条件发生变化

测试期间本机网关发生变化，用户已明确确认更换了 Wi-Fi / 地点。此后当前网络的
测试开始、结束地址一致。早期日志没有逐请求保存完整网络指纹，不能把所有中间
实验精确归到某个 Wi-Fi，也不能把换网后的成功视作代码修复。

当前网络的独立抓包只包含诊断脚本自己保留端口的 12 条 CDN 连接，每包截取
160 字节，没有捕获其他应用的连接。12 次 Cloudflare HTTP 请求全部返回 200；
9 条连接可见接收序列缺口及 SACK，6 条连接的内核计数出现重传，没有观察到
来自对端的 RST。该样本中的缺口均已恢复，最长观测恢复间隔约 0.303 秒。

这些抓包来自当前可用网络，不是原故障 Wi-Fi 的失败现场，不能替代原网络抓包。
抓包权限仅用于临时诊断；没有扩大 BPF 权限或更改网络设置。

## 当前网络的 CDN 节点验收

从生产实际下发的完整 Mihomo 和 Mihomo Modern 配置出发，在隔离客户端中
将“普通代理”和“AI 代理”均明确选择原有 CDN 节点。并非使用普通 VMess
节点替代 CDN 验收，也没有切换用户当前活动订阅。

| 请求 | Mihomo | Mihomo Modern | 验证范围 |
| --- | --- | --- | --- |
| Google 204 | 5/5 返回 204 | 5/5 返回 204 | 网络探测可达 |
| Google 首页 | 5/5 返回 200 | 5/5 返回 200 | 可跟随 Google HTTPS 跳转，没有 google.cn/m 跳转 |
| ChatGPT 匿名首页 | 5/5 返回 200 | 5/5 返回 200 | 没有 challenge 响应；未验证登录和对话 |
| OpenAI models，无密钥 | 5/5 返回 401 | 5/5 返回 401 | 仅证明 TLS 与鉴权端点响应 |

40 次请求全部收到预期网络响应，但这些小样本不代表所有网络或长期稳定性。
没有使用住宅代理作为 CDN 的前置入口，普通 Google 的出口设置没有更改。

另外，原 CDN 经过受控 HTTP fixture 的服务端 70 秒空闲场景后，WebSocket
和 SSE 都收到后续数据。客户端实际观察的两段数据间隔分别为 70.029 秒、
68.355 秒；两端计时起点和首包到达时间不同。该测试证明本轮 CDN 传输能够
持续连接，不是 ChatGPT 登录对话或 AI 住宅上游流式调用的验收。

同一 VPS 作为临时前置的链路也仅用于路径对照，没有写入生产订阅。
它依赖原有直连节点，不作为一个独立的 CDN 备用入口发布。
