# 普通代理自动择优与 CDN 诊断

## 发布状态

普通路由优化已提交，CDN 修复未通过公网验收。完整任务的合并、部署门槛尚未满足；本轮没有修改生产服务、主运行配置、Caddy、CDN 配置或用户当前活动客户端。

规格见 [adaptive-routing-cdn-spec.md](adaptive-routing-cdn-spec.md)。GitHub CI 与提交状态见 [PR #26](https://github.com/Zane-SI/RayLink/pull/26)。

## 普通路由改动

完整 YAML 订阅保留普通代理、AI 代理、未分类流量三个主组。普通代理默认选 RayLink 智能，同时提供故障回退、TCP 稳定和具体节点。sing-box 的普通 selector 同样改为默认智能组。

客户端实际探测全部已授权 TCP/UDP 协议。原实现会根据服务端 UDP 健康记录的缺失、时效、抖动和失败状态删除智能组候选，不能代表 Mac 或手机的当前网络。移除这道客户端候选过滤；服务端诊断记录及其有效期检查仍保留。

Mihomo 关闭 unified-delay，使择优考虑连接建立成本，而不是只使用后一次请求的 RTT。切换容差、证书验证和健康检查超时没有放宽；失败不回退到 DIRECT。AI 固定 Host、候选顺序、默认稳定组及住宅出口配置未改。

客户端已保存的选择不会被清空。若更新后普通代理仍选“故障回退”，需在该组选择一次“RayLink 智能”；AI 选择无需调整。

## 本地回归

- 完整单元/API 回归 827 项：826 通过、1 跳过、0 失败。
- sing-box 1.14.2 原生路由模拟：UDP 变快后被普通组选中，UDP 故障后 TCP 接管，延迟变化不改变健康 AI 出口或中断其持续流，所有候选失效时不走 DIRECT。降低 AI 容差的负对照确实失败。
- Mihomo 1.19.32：七种实际协议传输、错误证书拒绝、普通 UDP 故障后 TCP 接管、AI 回退和定时恢复通过。Modern 共享 provider 每节点一次完整连接探测，七节点共七次请求；传统格式仍各组探测。
- 原生国内 DNS、服务分流、AI 域名、固定 Host 与同机协议回退检查通过。
- 九种协议的 WebSocket 双向传输及 70 秒空闲后继续传输通过。首次调用误用不含 Naive outbound 的本地服务端二进制作为客户端，该轮失败；指定完整 sing-box 客户端后重跑通过。此项使用 Mihomo 1.19.25；不是生产 CDN 或已登录 AI 会话验收。

## 公网隔离对照

同一 Mac、物理 en0、隔离 Mihomo 1.19.32、TUN 关闭。以线上订阅为基线，在内存中仅应用待发布的普通组默认值、候选和测速设置；不是已部署订阅。原有节点字段及 AI 组逐项保持。两轮顺序对照样本很小，只说明当前网络的测量结果。

| 请求 | 旧默认中位数 | 自动择优中位数 | 结果 |
| --- | --- | --- | --- |
| X 匿名首页 | 1998 ms | 715 ms | 两边各 2/2 HTTP 200 |
| X PNG 图片 | 904 ms | 512 ms | 两边各 2/2，内容摘要一致 |
| Google 根页面 | 866 ms | 498 ms | 两边均跳转 google.com.hk |
| ChatGPT 匿名首页 | 2906 ms | 2864 ms | 两边各 2/2 HTTP 200，无 challenge |
| 百度 | 103 ms | 101 ms | 两边各 2/2 HTTP 200，直连规则保持 |

自动普通组实测选择 TUIC；ChatGPT、OpenAI API 仍经 VMess → AI 稳定出口。追加 Google 香港页 2/2 HTTP 200，约 1.28 秒；追加 ChatGPT 2/2 HTTP 200，约 2.94 和 5.46 秒，不能据此声称 AI 延迟已经改善。无密钥 API 返回 401 仅说明鉴权端点有响应。

服务端近期日志仍可见 ChatGPT/OpenAI 转发到 ai-residential；本轮没有修改住宅配置。日志抽样并非独占账号的逐请求出口 IP 证明。原生 App、iPhone、移动网络、登录及实际对话、X 信息流和视频未验收。

## CDN 阻断

强制选中原 CDN 节点后，六次 Google/ChatGPT/OpenAI 请求中五次约 5 秒失败，仅一次 API 返回 401，耗时约 8.88 秒。该结果不能认定 CDN 可用。

分段对照显示，Mac 到 Cloudflare 在 TLS 证书交换或 HTTP/WS 阶段超时，Cloudflare 自身的 /cdn-cgi/trace 也失败；该端点不经过 VPS 转发。相同时段源站 TLS/WS 正常。VPS 发起的 Cloudflare trace、Cloudflare WS、源站 WS 共 18 次全部取得预期状态。

其他受支持 HTTPS 端口、TLS 1.2/1.3、IPv6及 ECH 均未形成稳定修复。单独的 Go TLS 探针确认成功样本确实接受 ECH 并验证证书，但仍有握手超时。不同 SNI 的结果有差异，仍不足以唯一确定运营商、中间网络设备或 Cloudflare 的责任；不将丢包直接归因于 GFW。

MSS 参数实验未改变观测到的有效分段大小，不作为排除 MTU 问题的证据。没有据此修改系统 MTU。没有固定 Cloudflare IP、关闭证书验证、放大超时，或把另一普通节点的成功冒充 CDN 成功。

## Standards

独立审查未发现可执行的规范违例或新增代码异味。客户端策略改动未越过 Runtime、Host 权益和凭据边界，AI 固定 Host 的过滤及缓存保持。

## Spec

普通路由部分符合规格。仍有一项 P1 发布阻断：CDN 完整修复及同条件数据传输、70 秒空闲验收缺失。必须修复并验收，或由用户明确同意先单独发布普通路由优化，才能调整本轮完整发布范围。

本轮服务状态核对中，四个服务的 PID/InvocationID 与保护配置摘要均与此前基线一致。没有停止或重启既有节点。私有诊断日志与请求记录保存在 Git 忽略的本地 operations 目录，凭据及原始订阅不得公开。
